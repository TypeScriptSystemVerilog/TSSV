The 2026-10-12 port details, in short:
- Internal decodes `<R>_WE`/`<R>_RE` become `<R>_wr_hit`/`<R>_rd_hit` for every type.
- `WO` with `fields`: one output `<R>_field<i>` per field and one `<R>_we`.
- `constant` on any type but `RO` throws. A constant `RO` with no `reset` reads 0.
- `Memory` gets a `type` parameter: `bidi` (default), `rd_only` or `wr_only`. It is always
  part of the SV name, so `memory_32_32` becomes `memory_bidi_32_32`. `RAM` windows are `bidi`,
  `ROM` windows are `rd_only`.
- A `ROM` write is dropped and completes at once. It does not set the ROM's `<R>_last_q`.
- Windows are registered in both directions by default. `RAM`/`ROM` take `registerRequest` and
  `registerResponse`, both default `true`. Each flop that is on adds one wait state. With a
  zero-wait slave the default is 2 wait states. The human rejected pass-through as the default
  because `APB_to_Memory` drives `apb.PREADY` from `mem.READY` combinationally, so a path through
  the block reaches the APB master.

2. **Implement the ports in `ts/src/core/Registers.ts`**, exactly as §3 of
   `doc/framework/registers.md` says. Add `constant`, `registerRequest` and `registerResponse`
   to `Register`, and validate them (§3 lists what throws).
   - **Remove the flat ports.** Delete `<R>_ready`, `<R>_wdata`, `<R>_re`, `<R>_we`, `<R>_wstrb`
     and `<R>_rdata` for RAM/ROM, their flops, and the internal `<R>_ADDR`.
   - **Window state, per window.** With `registerRequest`, flop `ADDR` (`regs.ADDR - base`),
     `DATA_WR` and `WSTRB` on the capture edge and hold them, and drive `<R>.RE`/`<R>.WE` from a
     one-cycle flop. The slave sees the request in the cycle after the `regs` request and captures
     it on the next edge, so the block must not treat `<R>.READY` as completion until the cycle
     after it raised `RE`/`WE`. That needs an issue/wait state. Without `registerRequest`, drive
     the request combinationally from `regs`. With `registerResponse`, capture `<R>.DATA_RD` when
     the access completes, and drive `regs.READY` from a busy flop. Without it, `regs.READY` and
     `regs.DATA_RD` follow `<R>` during the wait.
   - **Read path (`addReadMux()`).** `regs.READY` is tied to `1'b1` today, with a comment naming
     this issue. `read_out` must take each window's data from its response flop or from
     `<R>.DATA_RD`.
   - **Constants.** A constant `RO` needs its own case in `read_mux`. Build its value from `reset`
     or from the field resets with the same placement as `fieldReadback()`.
   - **Draw the four timing cases** before coding them: a request at cycle 0, with a zero-wait
     slave and with a 2-wait slave. Check each against the `Memory` handshake.

## Assumptions

- `Memory`'s `WSTRB` is `ADDR_WIDTH/8` bits until #81 fixes it. `busAddressWidth` is typed as
  the literal `32`, so it is always 4 bits, which is wrong for a 64-bit `wordSize`. Pass
  `regs.WSTRB` through to `<R>.WSTRB` unchanged and leave the sizing to #81. Checked against the
  code on 2026-10-12.
- `regs.READY` is tied to `1'b1` in `addReadMux()`, and `read_out` reads windows from the flat
  `<R>_wdata`/`<R>_rdata` ports. Checked on 2026-10-12 (`ts/src/core/Registers.ts` lines 474
  and 484).
- `APB_to_Memory` passes `mem.READY` to `apb.PREADY` combinationally
  (`ts/src/modules/APB_to_Memory/APB_to_Memory.ts` line 56). So registered windows add APB wait
  states, and `tb_APB_to_Memory.sv` may need to tolerate them if its block has a window.
- `RegisterType.RO` has been an output port since commit 6d37281 (April 2024). ROM/RAM
  `<R>_rdata` were inputs until 4a3e066 (2024-08-02). That history is posted on the issue.

## Dead ends

- **Pass-through windows** (combinational request and response) were drafted and rejected on
  2026-10-12. They are allowed only as the opt-in `registerRequest: false, registerResponse: false`.
- **Tying a ROM's `WE`, `DATA_WR` and `WSTRB` low** was drafted and replaced by the `rd_only`
  `Memory` type.
- **Leaving `type` out of the `Memory` SV name for `bidi`** (to keep `memory_32_32`) was offered
  and rejected. Always include it.
- From #79: `verilator --lint-only -Wall --top-module <block>` on a block with an interface port
  still reports UNDRIVEN/UNUSED on the interface's signals. Only a wrapper top that drives the
  interface removes them, as `lintTop()` in `ts/test/test_RegisterBlock_read.ts` does. RAM/ROM
  `Memory` ports need the same treatment: the wrapper must also instantiate an interface for
  each window and expose it.
