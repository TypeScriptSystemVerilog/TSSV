1. **`ts/src/tb/patternRecord.ts`**: the record layout. It is tier 1, so it imports only
   `tssv/lib/core/TSSV`.
   - `RecordField { name, width }`.
   - `recordFields(intf: Interface, names?)`: the interface's `signals` in declaration order,
     with width 1 when none is given. `names` picks a subset, to leave out valid and ready.
   - `RecordLayout`: the fields, `radix: 'h' | 'b'`, each field's slot (low bit and width), and
     `wordWidth`.
     - Slots are packed MSB-first in field order.
     - In `'h'`, a slot is `4 * ceil(width / 4)` bits, and the pad bits are 0. In `'b'`, a slot
       is the field's exact width.
     - In `'h'`, a field wider than 16 bits is written as groups of 4 hex digits, counted from
       the LSB. The lead's example writes the 32-bit `data` as `data[31:16] _ data[15:0]`.
   - `packRecord()` and `unpackRecord()` convert between a `Record<string, bigint>` and a word.
     They throw on a value that is too wide, an unknown field, or a missing field.
2. **`ts/src/tb/patternFile.ts`**: the writer.
   - `formatPatternFile(layout, { dut, testcase, purpose, recordNoun, objectNoun, objects: [{ label, records }] })`

## Assumptions
- **The user's decision, 2026-10-30: PatternMemory reads synchronously**, `q <= mem[addr]`, the
  block-RAM form.
- **Read timing.** One synchronous read port can't show different records in the first two
  cycles after reset release:
  - every flop keeps its reset value until the first rising edge after release, so the address
    in the cycle after release is the address read during reset;
  - an address that uses `rst_b` as data would avoid that, but lint `-Wall` reports it as
    SYNCASYNCNET. #196 had to remove the same thing from SimTop (commit 9e8e5e2).

  So the tables get a priming cycle:
  - `VectorPlayer` gets a flop `run`, async reset to 0, with `d = 1`;
  - its output `fetch`, the address its tables read this cycle, is
    `!run ? 0 : (row >= rows-1 ? rows-1 : row+1)`;
  - `row` counts only while `run && !done`.

  Row 0 therefore lasts two cycles: the priming cycle and the next one. Each lane comes straight
  from the memory's output register, which is a flop, so a reset lane still meets SV guide RST-4.
  At `done`, `fetch` stays at `rows-1`, so the lanes hold their last value.

  A table of 4 rows (records m0 to m3). The clock runs throughout, and each column is one cycle.
  SimTop releases `rst_b` at the falling edge before `prime`.

  ```
  cycle       reset  reset │ prime │  c1   │  c2   │  c3   │  c4   │  c5   ...
  rst_b        0      0    │  1    │  1    │  1    │  1    │  1    │  1
  run          0      0    │  0    │  1    │  1    │  1    │  1    │  1
  row          0      0    │  0    │  0    │  1    │  2    │  3    │  4
  fetch        0      0    │  0    │  1    │  2    │  3    │  3    │  3
  done         0      0    │  0    │  0    │  0    │  0    │  0    │  1
  lane (q)     m0     m0   │  m0   │  m0   │  m1   │  m2   │  m3   │  m3
  checked      -      -    │  -    │ row 0 │ row 1 │ row 2 │ row 3 │  -
  Lfsr value   x0     x0   │  x0   │  x0   │  x1   │  x2   │  x3   │  x4     (step = run)
  ```

  WaveDrom for `testbench.md`:
  ```json
  { "signal": [
    { "name": "clk",   "wave": "p......." },
    { "name": "rst_b", "wave": "0.1....." },
    { "name": "run",   "wave": "0..1...." },
    { "name": "row",   "wave": "=...====", "data": ["0", "1", "2", "3", "4"] },
    { "name": "fetch", "wave": "=..===..", "data": ["0", "1", "2", "3"] },
    { "name": "done",  "wave": "0......1" },
    { "name": "lane",  "wave": "=...===.", "data": ["m0", "m1", "m2", "m3"] },
    { "name": "check", "wave": "0..1...0" }
  ]}
  ```

  What it changes:
  - `tb_SFIFOWave_dual_port` behaves the same. The SFIFO's reset is a table lane, held one cycle
    longer.
  - `tb_Lfsr` needs the Lfsr's `step` bound to `run`. Its value in row r is then still
    `xorshift[r]`.
  - The cycle counts in SimTop's PASS lines grow by one: 13 to 14 and 64 to 65.
  - This changes tier 1's timing contract. The docs say so, and the PR's Notes say why.
- `initial $readmemh("<file>", mem);` stays on one line after Verible formats it. This was checked

  generated module.
- TSSV itself (`ts/src/core/ModuleCheck.ts`) doesn't reject an `initial` written with

  `check-harness`.
- Verilator's `--lint-only -Wall --no-timing` accepts a memory written only by `$readmemh`. This
